# Deployment runbook

> Active production path: [`deploy/oracle/README.md`](../deploy/oracle/README.md)
> for Oracle Always Free + Neon + Caddy + Grafana Cloud. The Render Blueprint
> below is retained as a legacy alternative and is not the zero-cost,
> no-sleep deployment.

Production deploy of the macOS Troubleshooting Agent: Docker web service +
managed Postgres + weekly-credit cron, on Render. Everything is declared in
[`render.yaml`](render.yaml) — this doc is the operator's guide around it.

## Architecture in production

```
            Browser (Google Sign-In → session JWT)
                        │  HTTPS
                        ▼
      Render web service (Docker: Agent/Dockerfile)
        FastAPI + static frontend, migrations on boot
          │                    │                 │
          ▼                    ▼                 ▼
   Managed Postgres      Qdrant Cloud       LLM providers
   (users, credits,      (knowledge base)   (Groq / NVIDIA / …)
    cost ledger,                            + Tavily fallback
    feedback, AND the
    LangGraph checkpointer
    — conversation memory)
          ▲
          │  Monday 00:00 UTC
   Render Cron: python -m app.jobs reset-weekly-credits
```

- **State** lives in managed Postgres, **not** the container — the web service
  is stateless and safe to restart/redeploy.
- **Migrations** run automatically on startup (`app.main` lifespan → Alembic
  `upgrade head`). A fresh database reaches the current schema with no manual
  step; a half-migrated schema fails startup rather than serving.
- The KB is **not** in the image — it stays in Qdrant Cloud.

## First deploy

1. Push this repo to GitHub.
2. Render → **New → Blueprint** → select the repo. Render reads `render.yaml`
   and provisions the Postgres DB, the web service, and the cron job.
3. Fill in the secret env vars (Render prompts for every `sync: false` key):
   - `OPENAI_API_KEY`, `GROQ_API_KEY` — required for the agent to be "ready".
   - `QDRANT_URL`, `QDRANT_API_KEY` — the knowledge base.
   - `TAVILY_API_KEY` — optional web-search fallback.
   - `GOOGLE_CLIENT_ID` — set to enable Google Sign-In (leave unset to run in
     open mode). In Google Cloud Console, add the Render URL to the OAuth
     client's **Authorized JavaScript origins**.
   - `CORS_ORIGINS` — set to your exact frontend origin(s), comma-separated
     (e.g. `https://macos-agent.onrender.com`). Do **not** ship `*`.
   - `DATABASE_URL` and `AUTH_JWT_SECRET` are wired automatically (from the
     managed DB / generated by Render) — leave them alone.
4. First build runs migrations and comes up at `https://<service>.onrender.com`.
5. Verify: `scripts/smoke_test.sh https://<service>.onrender.com`.

## Verifying a deploy

```bash
scripts/smoke_test.sh https://<service>.onrender.com          # public checks, no spend
METRICS_TOKEN=... scripts/smoke_test.sh https://<service>...  # strongest gate
scripts/smoke_test.sh https://<service>.onrender.com --full   # + one real chat turn
```

Exit 0 = healthy. Wire this as a post-deploy gate; a non-zero exit is a
rollback trigger.

The assertions adapt to how the target is configured, so a hardened deployment
does not false-fail: without `METRICS_TOKEN` the metrics check accepts 200 **or**
401 (both correct depending on `APP_ENV`), and when Google auth is enabled the
chat probes assert 401, because `Depends(current_user)` resolves before the
handler body and the guardrails never run. Guardrail *logic* is covered by
`Agent/backend/tests/test_guardrails.py`; set `SMOKE_BEARER` to a session JWT if
you want the gate to exercise it through the API too.

Also glance at `GET /health`: `ready: true` means all required credentials
resolved and the agent built, and `checkpointer` reports which tier is live —
`memory` against a Postgres `DATABASE_URL` means conversation memory silently
degraded and every session is being lost on restart.

## Rollback

Render keeps every prior image. To roll back:

1. Render dashboard → the web service → **Deploys** → pick the last-good
   deploy → **Rollback to this version**. (Or `autoDeploy: false` + redeploy a
   known-good commit.)
2. **Migrations are forward-only here** — each release adds tables, never drops
   or rewrites existing columns, so rolling the *code* back is safe against a
   newer schema. If a release ever ships a destructive migration, add its
   `downgrade()` path and run `alembic downgrade -1` before rolling code back.
3. Re-run the smoke test against the rolled-back instance.

## Weekly-credit cron

The `macos-agent-weekly-credits` cron runs `python -m app.jobs
reset-weekly-credits` every Monday 00:00 UTC against the same Postgres. It is
idempotent and belt-and-braces with the lazy per-access reset in
`app/credits.py` — running it twice is harmless. Trigger it manually from the
Render cron's dashboard to test, and confirm the `weekly credits reset` log
line (with the account count) appears.

## Observability in production

- **Metrics**: `GET /metrics` is live. Point a hosted Prometheus (e.g. Grafana
  Cloud's) at it, or run Grafana Agent as a sidecar to remote-write the
  scrape. Import the dashboard from
  [`observability/grafana/dashboards/macos_agent.json`](../observability/grafana/dashboards/macos_agent.json).
- **Logs**: the app logs one JSON object per line to stdout — Render ships
  stdout to its log stream; forward to Loki/Grafana Cloud for the dashboards'
  log panels. Key fields: `cost_usd`, `error_type`, `pii_counts`, `rating`.
- **Exact cost / billing truth** lives in the `usage_log` and `credit_accounts`
  Postgres tables, not Prometheus (whose counters reset on restart).

## Scaling notes

- **Conversation memory is Postgres-backed (V3)** — `make_memory_checkpointer()`
  automatically uses the same `DATABASE_URL` as the relational schema when it
  points at Postgres, so a follow-up turn routed to a different worker (or a
  brand-new container after a redeploy) still sees the full case file and
  message history. `WEB_CONCURRENCY` is safe to raise above 1 for this reason
  alone. (Local dev without Postgres falls back to `AGENT_CHECKPOINT_DB`
  SQLite, then an in-memory store — see `Agent/backend/app/agent/graph.py`.)
- Render's **free Postgres expires ~30 days** after creation and free web
  services **spin down when idle** (first request after idle is slow). Upgrade
  both plans for anything beyond a demo.
- `db_pool_size` / `db_max_overflow` (default 5/5) cap DB connections — keep
  them under the Postgres plan's connection limit.

## Landing page and application routes

- `GET /` serves the static V3 project landing page.
- `GET /app` serves the existing chat frontend.
- API routes remain at `/health`, `/metrics`, `/auth/*`, `/chat`, and
  `/feedback`; they are declared before either static mount.
- The landing page reads `/health` and `/metrics` on load. If the deployment
  protects metrics at the network edge later, the page simply shows an
  unavailable metrics state and the chat app remains unaffected.
